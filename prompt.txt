You are acting as a senior software architect and principal engineer helping me build a new developer tool called **AEM Doctor**.

## Product vision

AEM Doctor is intended to become a developer diagnostics platform for Adobe Experience Manager.

Its long-term purpose is to diagnose:

* Maven dependency problems
* OSGi Import-Package / Export-Package problems
* AEM version compatibility problems
* Java version compatibility
* AEM Forms dependency issues
* Core Components compatibility
* Cloud Manager preflight problems
* Dispatcher problems
* Content package problems
* migration risks
* common AEM architectural issues

However, **do not attempt to build the full platform yet**.

We are building a deliberately small technical proof of concept:

# AEM Doctor 0.0.1

The goal of version 0.0.1 is to prove that we can analyze a real AEM Maven project and diagnose OSGi dependency problems automatically.

The application must run locally and must not require an AEM server.

---

# Core MVP objective

Given an AEM project directory, AEM Doctor should:

1. Recursively discover Maven `pom.xml` files.
2. Parse Maven project/module information.
3. Discover compiled `.jar` files under module `target` directories.
4. Open those JAR files and read `META-INF/MANIFEST.MF`.
5. Extract relevant OSGi metadata.
6. Build an in-memory package dependency graph.
7. Compare `Import-Package` requirements against available `Export-Package` declarations.
8. Detect unresolved packages.
9. Detect incompatible OSGi package version ranges.
10. Produce a human-readable terminal report explaining the problem.

Do not introduce AI or LLM APIs in this version.

The diagnostic engine must be deterministic.

# JAR discovery

For each Maven module, inspect likely compiled artifacts under:

```text
target/*.jar
```

Ignore:

```text
*-sources.jar
*-javadoc.jar
original-*.jar
```

Do not modify the JAR.

Read:

```text
META-INF/MANIFEST.MF
```

# OSGi manifest parsing

Extract at minimum:

```text
Bundle-SymbolicName
Bundle-Version
Import-Package
Export-Package
Require-Capability
Provide-Capability
```

The most important fields for this MVP are:

```text
Import-Package
Export-Package
```

Correctly handle multi-line MANIFEST.MF continuation syntax.

Correctly parse comma-separated package declarations where attributes may contain commas or quoted values.

For example:

```text
Import-Package:
 com.example.foo;version="[1.0,2.0)",
 com.example.bar;version="[5.12,5.13)"
```

should become structured objects.

---

# OSGi version handling

Implement proper semantic comparison for OSGi-style versions.

Support forms such as:

```text
1
1.2
1.2.3
1.2.3.qualifier
5.12.3
```

Support ranges such as:

```text
[1.0,2.0)
[5.12,5.13)
(1.0,2.0]
[1.0,)
(,2.0)
```

Remember:

```text
[ = inclusive
( = exclusive

] = inclusive
) = exclusive
```

Do not rely on ordinary JavaScript string comparison.

Create unit tests for version and version-range behavior.

# Dependency graph

Construct a graph representing something similar to:

```text
Bundle
  imports
    Package X [version range]

Package X
  exported by
    Bundle Y version Z
```

Given an imported package:

```text
com.adobe.cq.forms.core.components.models.form
```

AEM Doctor should be able to answer:

```text
Who imports this?
Who exports this?
Which version is exported?
What version range is required?
Does the exported version satisfy the import range?
```

Design this graph so it can later support multiple providers for the same package.

# Diagnostic rules for 0.0.1

Implement these initial deterministic rules.

## AD-OSGI-001

### Missing exported package

Example:

```text
Import:
com.example.foo

No bundle in the analyzed project exports the package.
```

Output an ERROR or CRITICAL finding.

Important:

Because version 0.0.1 only sees project bundles, clearly explain that the package could potentially be supplied by the AEM runtime or another external bundle.

Do not claim definitively that the dependency is missing from AEM.

Phrase the result accurately.

Example:

```text
No provider for com.example.foo was found among the analyzed project bundles.

This package may be supplied by the AEM runtime or another external dependency.
```

---

## AD-OSGI-002

### OSGi version mismatch

Example:

```text
Consumer requires:
[5.12,5.13)

Provider exports:
5.11.2
```

Report:

```text
Required:
>= 5.12.0 and < 5.13.0

Available:
5.11.2

Result:
INCOMPATIBLE
```

---

## AD-OSGI-003

### Compatible package

For debugging purposes, allow an optional verbose mode that reports successful resolutions.

Example:

```text
com.adobe.foo

Required:
[1.0,10.0)

Available:
5.12.3

Result:
COMPATIBLE
```

Do not clutter normal output with every successful package resolution.

---

## AD-OSGI-004

### Suspicious broad version range

Detect unusually broad ranges such as:

```text
[1.0.0,10.0.0)
```

This should be a WARNING, not an error.

Explain that the dependency technically resolves but the range spans many major versions and could permit runtime resolution against APIs that were not tested with the application.

Make the threshold configurable in code.

# Current real-world test case

One of the real AEM dependency scenarios that motivated this product involves:

```text
Package:
com.adobe.cq.forms.core.components.models.form

Exported version:
5.12.3

Provider:
com.adobe.aem.core-forms-components-af-core
```

Consumers can include ranges such as:

```text
formsgenai-core
[1.0.0,10.0.0)

com.adobe.aemds.guide.aemds-guide-addon-impl
[1.0.0,10.0.0)

com.adobe.aem.core-forms-print-components-print-core
[5.12,5.13)
```

For this scenario the engine should correctly determine that:

```text
5.12.3 ∈ [1.0.0,10.0.0)

and

5.12.3 ∈ [5.12,5.13)
```

Therefore the presence of these package relationships alone does **not** represent a version incompatibility.

The engine should not invent a root cause.

A key principle of AEM Doctor is:

> Report what the evidence proves, distinguish it from what is only suspected, and never manufacture a diagnosis.
